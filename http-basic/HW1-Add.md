1. rest api의 예시로,  /getUserInfo와 같이 동사를 url경로로 사용했는데, resuful 한 설계를 하기 위해서 어떻게 수정할 수 있을까요? 다른 예시들도 바꿔보세요.

/getUserInfo는 restful하지 않는 이유는 행위와 대상을 구분하지 않았기 때문입니다. 
먼저 메서드 GET을 쓰고 / 로 구분한 후 목적에 맞는 대상들을 하나씩 구분해야합니다. 따라서 GET /User/info 라고 써도 되지만 info가 가리키는 대상이 애매모호할 수 있기에 확실한 대상을 사용하는 것이 맞다고 생각합니다.
이에 따라 restful하게 GET /user/{id}로 수정할 수 있을 것 같습니다.

2. 추가로 회원가입과 비밀번호 변경 작업의 api url은 어떻게 설계해야하고, 상태코드는 무엇을 반환해야할까요?

회원가입의 경우는 새로운 사용자를 생성하는 것이므로 POST를 사용하여야 하고 비밀번호 변경 작업은 사용자 데이터의 전체 변경이 아닌 비밀번호라는 부분변경이므로 PUT이 아닌 PATCH를 사용해야합니다.
따라서 예를 들은 API URL은 POST /user와 PATCH /user/{id}/password 입니다. 

회원가입의 경우 POST와 관련된 요청 성공시 새로운 리소스가 생성되었다는 201 Created를, 실패시에는 400 Bad Request를 반환해야합니다.
비밀번호 변경 작업시에 성공시 200 OK, 변경요청한 사용자가 없을 시 404 Not Found를 반환해야합니다.

3. http인증 헤더에 대해 잘 정리했습니다. 프론트에서 헤더로 토큰을 주는 로직과, 백엔드에서 헤더의 토큰을 파싱해 검증하는 로직을 간단하게 구성해보면 좋을 것 같습니다.

이 부분은 조금 더 공부해오겠습니다.

4. put, patch의 멱등성도 어떻게 되는지 공부하면 좋을 것 같습니다.

PUT은 서버에 덮어쓰는 내용이 중간에 변경되지 않는다면 멱등성이 보장됩니다. 하지만 PATCH의 경우에는 멱등성이 보장될 수도 아닐 수도 있습니다.
PATCH는 리소스의 일부를 수정한다는 의미를 가지기에 같은 필드를 같은 내용으로 수백번 반복해도 멱등성을 가집니다. 
하지만 연산 누적의 경우 서버의 초기상태에 있는 필드 LoginCount가 0일때 PATCH로 증가/누적되게 만들었다면 요청마다 달라지기에 멱등성을 가지지 않습니다.

5. tcp와 udp의 차이점, 그리고 quic에 대해서도 공부하면 좋을 것 같습니다.

TCP는 연결지향형 UDP는 비연결지항형입니다. TCP는 3 Way Handshake로 연결 4 Way Handshake로 해제하게 됩니다. 
하지만 UDP의 경우, 이러한 연결절차가 없고 단순히 발신자가 데이터를 보내기에 데이터 패킷 손실 확률이 더 높습니다.
이러한 UDP는 단순히 보낸다에 초점이 맞췄기에 속도 부분에 있어서는 TCP보다 빠릅니다.

QUIC는 TCP에서의 신뢰성, UDP에서의 속도라는 두마리 토끼를 잡기 위해 구글에서 개발한 최신 프로토콜입니다.
기본적으로 UDP위에서 동작합니다. 또한 TCP의 핸드쉐이크 과정의 느림을 보안하기 위해 0-RTT를 지원하는데, 이전 연결정보가 있다면 핸드쉐이크 없이 바로 데이터를 전송가능합니다.
또한 Time Loss Detection (TLD) 기능으로 일정시간 수신측으로부터 ACK를 받지 못한 경우 해당 패킷을 재전송할때까지 기다리지 않고 다른 패킷을 우선적으로 보내 패킷 손실을 회피함으로써 신뢰성을 보장하게 됩니다.
